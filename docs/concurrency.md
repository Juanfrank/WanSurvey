# Many users at once

What the API does so that hundreds of interviewers, supervisors and web respondents can use it at the same time, and how to size it. The research behind each choice is listed at the end.

## What is in place

| Concern                        | What WanSurvey does                                                                                                                                                                                                                                                                                                                                                                                           | Where                                                         |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Database connections           | A bounded pool per process (`DB_POOL_MAX`, worker `DB_WORKER_POOL_MAX`); idle connections are closed after `DB_IDLE_TIMEOUT_S` and every connection is renewed after `DB_MAX_LIFETIME_S`, so a pooler restart or a failover never leaves dead connections in the pool                                                                                                                                         | `apps/api/src/db/database.ts`                                 |
| Pooler compatibility           | Tenant, user and time limits are set per transaction with `set_config(…, true)`, never with session-level `SET`; no session advisory locks, no `LISTEN/NOTIFY`. Works behind PgBouncer in transaction mode (Azure's built-in one on port 6432) with `DB_PREPARE=false`                                                                                                                                        | same                                                          |
| Runaway queries and lock waits | Each request's transaction gets `statement_timeout` (`DB_STATEMENT_TIMEOUT_MS`, 30 s), `lock_timeout` (`DB_LOCK_TIMEOUT_MS`, 5 s) and `idle_in_transaction_session_timeout` (`DB_IDLE_IN_TRANSACTION_MS`, 60 s); jobs get a longer statement time (`DB_WORKER_STATEMENT_TIMEOUT_MS`, 10 min). Hitting a limit answers **503 BUSY** instead of holding a connection                                            | same                                                          |
| Conflicts between transactions | A deadlock (`40P01`) or serialization failure (`40001`) rolls the transaction back entirely; it is run again, up to three times, after a short random pause                                                                                                                                                                                                                                                   | same                                                          |
| Deadlock prevention            | Rows locked in batches are locked in one global order (interview sync sorts by id); queues use `SELECT … FOR UPDATE SKIP LOCKED` (CATI, e-mail dispatch) so callers never wait on each other's rows                                                                                                                                                                                                           | `interviews.service.ts`, `cati.service.ts`, `cawi.service.ts` |
| Lost updates                   | Questionnaire drafts carry a revision (optimistic concurrency, merge or ask); interview changes are numbered per device and replayed idempotently                                                                                                                                                                                                                                                             | `questionnaires.controller.ts`, `interviews.service.ts`       |
| Overload                       | At most `MAX_CONCURRENT_REQUESTS` (200) requests are handled at once per API process; beyond that it answers 503 with `Retry-After` at once (load shedding) instead of queueing without limit. The web app retries reads after the time given; devices sync again with back-off                                                                                                                               | `common/load-shed.ts`, `web/src/api.ts`                       |
| Rate limits                    | Counters in Redis when it is configured, so every instance counts the same requests. Signed-in routes count per session (interviewers in one office behind one public IP do not share a quota); public routes (sign-in, respondents) count per IP so invented cookies cannot get round them; every route also has an overall per-IP ceiling (`RATE_LIMIT_PER_IP`). If Redis is down, requests are let through | `common/throttle.ts`                                          |
| Queueing                       | BullMQ on Redis: light jobs (e-mail, live figures, privacy) and heavy ones (exports) have separate queues and workers (`JOB_CONCURRENCY`, `HEAVY_JOB_CONCURRENCY`), so a big export never delays e-mail. Jobs retry three times with exponential back-off; a job id makes enqueueing idempotent; failed jobs are kept a week (at most 500). Redis must use `maxmemory-policy noeviction`                      | `jobs/jobs.service.ts`                                        |
| Hot reads                      | Compiled questionnaires (immutable once published) are cached in memory per process (least recently used, 100 versions): the respondent page, sync and submit no longer read them from the database each time. Live dashboards of one project share one snapshot per second instead of one query per viewer                                                                                                   | `interviews/compiled-cache.ts`, `dashboard/live.service.ts`   |
| Keep-alive                     | `HTTP_KEEPALIVE_MS` (65 s) is longer than the load balancer's idle timeout and `headersTimeout` longer still, so the balancer never reuses a connection the API has just closed (the cause of sporadic 502s)                                                                                                                                                                                                  | `app.ts`                                                      |
| Shutdown                       | On SIGTERM the API stops taking requests, the worker finishes its jobs, and database pools, queues, the bus and rate-limit connections close                                                                                                                                                                                                                                                                  | `enableShutdownHooks`, `onModuleDestroy`                      |

## Sizing on Azure App Service S1

Every process holds its own pool, so the database sees at most:

```
API instances × DB_POOL_MAX + worker instances × DB_WORKER_POOL_MAX (+ migrations, admin)
```

This must stay below the server's `max_connections` minus the connections Azure reserves. On small burstable servers `max_connections` is low (it is computed from memory when the server is created; about 25 per GiB on the smallest ones), so:

| Setup                                               | Suggested settings                                                                                                                                                                                   |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Testing: 1 API + 1 worker, Burstable B1ms           | `DB_POOL_MAX=10`, `DB_WORKER_POOL_MAX=5` (15 connections)                                                                                                                                            |
| Fieldwork: 3 API + 1 worker, B2s or General Purpose | `DB_POOL_MAX=15`, `DB_WORKER_POOL_MAX=5` (50), or turn on the built-in PgBouncer                                                                                                                     |
| Many instances or bursts                            | Built-in PgBouncer (`pgbouncer.enabled=true`, port 6432, transaction mode), point `DATABASE_URL` at port 6432 and set `DB_PREPARE=false`; the pools can then be larger than the server's connections |

Keep `JOB_CONCURRENCY + HEAVY_JOB_CONCURRENCY` at or below `DB_WORKER_POOL_MAX`, and `MAX_CONCURRENT_REQUESTS` well above what one instance serves in normal use (it is a safety valve, not a throttle). Check with the k6 scripts in `load/` before a large wave; for those, raise `RATE_LIMIT_PER_IP` (all virtual users come from one address).

## Settings

| Variable                                                           | Default          | Meaning                                        |
| ------------------------------------------------------------------ | ---------------- | ---------------------------------------------- |
| `DB_POOL_MAX` / `DB_WORKER_POOL_MAX`                               | 10 / 5           | Connections per API / worker process           |
| `DB_IDLE_TIMEOUT_S` / `DB_MAX_LIFETIME_S` / `DB_CONNECT_TIMEOUT_S` | 30 / 1800 / 10   | Pool housekeeping (seconds)                    |
| `DB_PREPARE`                                                       | `true`           | `false` behind a transaction-mode pooler       |
| `DB_STATEMENT_TIMEOUT_MS` / `DB_WORKER_STATEMENT_TIMEOUT_MS`       | 30 000 / 600 000 | Longest statement for a request / a job        |
| `DB_LOCK_TIMEOUT_MS`                                               | 5 000            | Longest wait for a row lock                    |
| `DB_IDLE_IN_TRANSACTION_MS`                                        | 60 000           | A transaction left idle is ended by the server |
| `MAX_CONCURRENT_REQUESTS`                                          | 200              | Per API process; 0 turns load shedding off     |
| `RATE_LIMIT_PER_IP`                                                | 5 000 / min      | Ceiling per address over all routes            |
| `JOB_CONCURRENCY` / `HEAVY_JOB_CONCURRENCY`                        | 4 / 1            | Jobs at once per worker process                |
| `HTTP_KEEPALIVE_MS`                                                | 65 000           | Keep-alive of the API's HTTP server            |

## Sources

- Microsoft, [PgBouncer in Azure Database for PostgreSQL flexible server](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-pgbouncer) and [connection pooling best practices](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/concepts-connection-pooling-best-practices): built-in PgBouncer, off by default, port 6432, transaction mode.
- Microsoft, [max_connections and connection settings](https://learn.microsoft.com/en-us/azure/postgresql/flexible-server/server-parameters-table-connections-and-authentication-connection-settings): computed from the compute size at creation (memory × 25 on small servers), not changed when the size changes.
- [PgBouncer pooling without surprises](https://privatedevops.com/articles/pgbouncer-pooling-without-surprises) and [connection pooling with PgBouncer](https://oneuptime.com/blog/post/2026-02-16-how-to-set-up-connection-pooling-with-pgbouncer-in-azure-database-for-postgresql/markdown): what transaction mode breaks (session `SET`, session advisory locks, `LISTEN/NOTIFY`, server-side prepared statements).
- [Postgres timeouts explained](https://www.bytebase.com/blog/postgres-timeout/) and [the three timeout parameters](https://haiderzdbre.substack.com/p/the-postgresql-trinity-the-3-timeout): `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout`, set per role or per transaction, on the server rather than the pooler.
- BullMQ, [Going to production](https://docs.bullmq.io/guide/going-to-production): `noeviction`, `maxRetriesPerRequest: null`, removing finished jobs, retries with back-off.
- NestJS, [rate limiting](https://docs.nestjs.com/v9/security/rate-limiting): the default storage is in memory per instance; shared storage for several instances.
- [Random 502 errors behind a load balancer](https://www.flightcontrol.dev/docs/troubleshooting/load-balancer-502-keepalive-timeout): keep-alive longer than the balancer's idle timeout, headers timeout longer still.
