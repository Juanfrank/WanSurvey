# Many users at once

What the API does so that hundreds of interviewers, supervisors and web respondents can use it at the same time, and how to size it. The research behind each choice is listed at the end.

## What is in place

| Concern                        | What WanSurvey does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Where                                                         |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Database connections           | A bounded pool per process (`DB_POOL_MAX`, worker `DB_WORKER_POOL_MAX`); a connection that fails is dropped and replaced on the next use                                                                                                                                                                                                                                                                                                                                                                                  | `apps/api/src/db/mssql/connection.ts`                         |
| Tenant context                 | The organisation and the acting person are set in `SESSION_CONTEXT` at the start of each transaction and cleared at its end, because pooled connections are reused; the security policy reads them. Nothing relies on session state that outlives a transaction                                                                                                                                                                                                                                                           | `apps/api/src/db/mssql/database.ts`                           |
| Runaway queries and lock waits | A request's statements stop after `DB_STATEMENT_TIMEOUT_MS` (30 s; the driver's request timeout) and a lock wait after `DB_LOCK_TIMEOUT_MS` (5 s, `SET LOCK_TIMEOUT` put in front of every statement, since each one runs in its own `sp_executesql`); jobs get a longer statement time (`DB_WORKER_STATEMENT_TIMEOUT_MS`, 10 min). Hitting a limit answers **503 BUSY** instead of holding a connection                                                                                                                  | same                                                          |
| Conflicts between transactions | A deadlock victim (error 1205) rolls the transaction back entirely; it is run again, up to three times, after a short random pause                                                                                                                                                                                                                                                                                                                                                                                        | same                                                          |
| Deadlock prevention            | Rows locked in batches are locked in one global order (interview sync sorts by id); queues use `UPDLOCK, READPAST` hints (CATI, e-mail dispatch) so callers never wait on each other's rows                                                                                                                                                                                                                                                                                                                               | `interviews.service.ts`, `cati.service.ts`, `cawi.service.ts` |
| Lost updates                   | Questionnaire drafts carry a revision (optimistic concurrency, merge or ask); interview changes are numbered per device and replayed idempotently                                                                                                                                                                                                                                                                                                                                                                         | `questionnaires.controller.ts`, `interviews.service.ts`       |
| Overload                       | At most `MAX_CONCURRENT_REQUESTS` (200) requests are handled at once per API process; beyond that it answers 503 with `Retry-After` at once (load shedding) instead of queueing without limit. By priority: opening an open link is turned away from 60 % of the limit, the steps of interviews under way (a respondent's survey, a device's sync or submission) go on up to twice the limit, so a started interview is not cut halfway. The web app retries reads after the time given; devices sync again with back-off | `common/load-shed.ts`, `web/src/api.ts`                       |
| Rate limits                    | Counters in Redis when it is configured, so every instance counts the same requests. Signed-in routes count per session (interviewers in one office behind one public IP do not share a quota); public routes (sign-in, respondents) count per IP so invented cookies cannot get round them; every route also has an overall per-IP ceiling (`RATE_LIMIT_PER_IP`). If Redis is down, requests are let through                                                                                                             | `common/throttle.ts`                                          |
| Queueing                       | BullMQ on Redis: light jobs (e-mail, live figures, privacy) and heavy ones (exports) have separate queues and workers (`JOB_CONCURRENCY`, `HEAVY_JOB_CONCURRENCY`), so a big export never delays e-mail. Jobs retry three times with exponential back-off; a job id makes enqueueing idempotent; failed jobs are kept a week (at most 500). Redis must use `maxmemory-policy noeviction`                                                                                                                                  | `jobs/jobs.service.ts`                                        |
| Hot reads                      | Compiled questionnaires (immutable once published) are cached in memory per process (least recently used, 100 versions): the respondent page, sync and submit no longer read them from the database each time. Live dashboards of one project share one snapshot per second instead of one query per viewer                                                                                                                                                                                                               | `interviews/compiled-cache.ts`, `dashboard/live.service.ts`   |
| Keep-alive                     | `HTTP_KEEPALIVE_MS` (65 s) is longer than the load balancer's idle timeout and `headersTimeout` longer still, so the balancer never reuses a connection the API has just closed (the cause of sporadic 502s)                                                                                                                                                                                                                                                                                                              | `app.ts`                                                      |
| Shutdown                       | On SIGTERM the API stops taking requests, the worker finishes its jobs, and database pools, queues, the bus and rate-limit connections close                                                                                                                                                                                                                                                                                                                                                                              | `enableShutdownHooks`, `onModuleDestroy`                      |

## One interview on several devices

Changes are numbered per device (`interview_devices.last_seq`), as before. The interview's snapshot (`state`) belongs to the whole interview, so it carries a version of its own:

- Every write of `state` bumps `interviews.state_version` and records the device that wrote it (`state_device`; `review` for a reviewer's correction). Payloads give `stateVersion` and `ownState` (this device wrote it last).
- A sync item may carry `baseVersion`, the version its snapshot builds on. The snapshot is written only when the batch brought new changes and none was missed (a late or repeated batch carries an older snapshot), and, when `baseVersion` is given, only if it is the server's version or this device wrote the newer one itself (its last answer was lost). Otherwise the changes are still recorded and acknowledged, the snapshot is not, and the item reports `STALE_STATE`. The answer gives `versions[id]`, the version the snapshot was written as.
- On opening, a device takes the server's copy when it has nothing left to send, when the server acknowledged more than it numbered, or when another device or a reviewer wrote a version newer than the one its copy builds on. Otherwise its own copy, with its unsent changes, goes on (`alignCopy` in `web/src/interview/store.ts`).
- Devices that predate versions send no `baseVersion` and keep working: their snapshots are written as before, except a late or repeated batch's.

Codes given to "other" texts (`<VAR>_CODE`) are not in the snapshot; rebuilding `answers` from a snapshot, by a sync or a correction, keeps each code while its text is unchanged.

## Sizing on Azure App Service

Every process holds its own pool, so the database sees at most:

```
API instances × DB_POOL_MAX + worker instances × DB_WORKER_POOL_MAX (+ migrations, admin)
```

This must stay below what the database tier allows (concurrent sessions and workers: see the limits of your Azure SQL tier or the SQL Server's `max user connections`). Start with these and measure:

| Setup                                                            | Suggested settings                                                     |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Testing: 1 API + 1 worker                                        | `DB_POOL_MAX=10`, `DB_WORKER_POOL_MAX=5` (15 connections)              |
| One App Service P0v3 (API + worker per instance), autoscale to 2 | `DB_POOL_MAX=10`, `DB_WORKER_POOL_MAX=5` (15 per instance, 30 at most) |
| Fieldwork: 3 API + 1 worker                                      | `DB_POOL_MAX=15`, `DB_WORKER_POOL_MAX=5` (50)                          |

Keep `JOB_CONCURRENCY + HEAVY_JOB_CONCURRENCY` at or below `DB_WORKER_POOL_MAX`, and `MAX_CONCURRENT_REQUESTS` well above what one instance serves in normal use (it is a safety valve, not a throttle). Check with a load test (k6) on a staging copy before a large wave; for it, raise `RATE_LIMIT_PER_IP` (all virtual users come from one address).

## Settings

| Variable                                                     | Default          | Meaning                                    |
| ------------------------------------------------------------ | ---------------- | ------------------------------------------ |
| `DB_POOL_MAX` / `DB_WORKER_POOL_MAX`                         | 10 / 5           | Connections per API / worker process       |
| `DB_STATEMENT_TIMEOUT_MS` / `DB_WORKER_STATEMENT_TIMEOUT_MS` | 30 000 / 600 000 | Longest statement for a request / a job    |
| `DB_LOCK_TIMEOUT_MS`                                         | 5 000            | Longest wait for a row lock                |
| `MAX_CONCURRENT_REQUESTS`                                    | 200              | Per API process; 0 turns load shedding off |
| `RATE_LIMIT_PER_IP`                                          | 5 000 / min      | Ceiling per address over all routes        |
| `JOB_CONCURRENCY` / `HEAVY_JOB_CONCURRENCY`                  | 4 / 1            | Jobs at once per worker process            |
| `HTTP_KEEPALIVE_MS`                                          | 65 000           | Keep-alive of the API's HTTP server        |

## Sources

- BullMQ, [Going to production](https://docs.bullmq.io/guide/going-to-production): `noeviction`, `maxRetriesPerRequest: null`, removing finished jobs, retries with back-off.
- NestJS, [rate limiting](https://docs.nestjs.com/v9/security/rate-limiting): the default storage is in memory per instance; shared storage for several instances.
- [Random 502 errors behind a load balancer](https://www.flightcontrol.dev/docs/troubleshooting/load-balancer-502-keepalive-timeout): keep-alive longer than the balancer's idle timeout, headers timeout longer still.
